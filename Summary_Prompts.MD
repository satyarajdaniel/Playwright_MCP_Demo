MCP:
>> LLM's can only summarise, visualise data provided they cannot fetch realtime 
Ex: OpeanAi API >> LLM, ChatGPT >> Agent/Tool (which will fetch provide lates info & provide it to LLM )
>> So Any AI application contains, LLM + tools& knowledge(API's, Tools, Websearch, DB, Files), so we will write code for interaction between them or build agentic framework. to standardise connecting LLMS with tools & knowledge, Anthropic introduced MCP protocol.

POST MCP:
LLM >> MCP >> MCP Server (LLM Through MCP will interact with MCP server (Yahoo API, or tools builds their MCP server )), although there is a small glue code for LLM MCP interaction

PLAYWRIGHT MCP:
>> We can download PLAYWRIGHT MCP in either of VS/Cursor/Claude code editors. (In code editors We need to select our LLM which will act as MCP client/Agent)

It gives us Three Agents:
>> These three agents are just markdown files, which has instructions for each agents

1)Planner
>Explores the app in a real browser and writes a plain-English test plan. Never touches code.
Ex:
Input
A URL and an instruction like "cover the checkout flow"
Output
A numbered Markdown test plan in specs/*.md
Constraint
Read-only browser. No destructive clicks. Writes only to specs/.

2)Generator
>Turns a plan scenario into runnable Playwright TypeScript that follows your framework conventions.

Ex:
Input
A plan file and a scenario number
Output
A Playwright .spec.ts file that runs and passes
Constraint
Verifies locators in a live browser before writing them. Asks before creating new page objects.

3)Healer
>>Diagnoses failing tests and fixes them — without weakening assertions or hiding real bugs.

Input
A failing test file
Output
A minimum-viable fix + a mandatory report explaining what was done
Constraint
Preserves assertion intent. Never softens tests. Never skips silently. Stops after 2 failed attempts.

2. Read the error output carefully
3. Open the app in a live browser to inspect the actual DOM
4. Determine root cause
5. Apply the minimum-viable fix
6. Preserve assertion intent — do NOT weaken any assertion
7. Do NOT add waitForTimeout
8. Do NOT skip the test
9. Re-run twice to confirm stability
